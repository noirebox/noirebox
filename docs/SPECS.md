# Specifications — NoireBox v0.1.0

*This document is the source of truth: data contracts, cryptographic algorithms,
API contracts, and measured performance. Any divergence between code and spec is a bug.*

Machine-readable OpenAPI spec: [`docs/openapi.json`](openapi.json) (generated by FastAPI — same as `/docs` and `/redoc` on the running API).

---

## 1. Overview

NoireBox is a Python service (FastAPI) that provides two guarantees to an AI-agent system:

1. **Provable traceability**: every event (LLM call, output, incident, evaluation) is sealed in a tamper-evident journal that is exportable and verifiable by a third party without access to the server.
2. **Filtering of hostile inputs**: meeting transcripts are scanned before the agent by two interchangeable engines.

```
transcript ──▶ guardrail (regex | ml) ──▶ agent (any)
                    │ incident                        │ llm_call / llm_output
                    ▼                                 ▼
              ┌───────────────── TAMPER-EVIDENT JOURNAL ─────────────────┐
              │  SQLite append-only · SHA-256 chain · Ed25519           │
              └───────────────────────────┬───────────────────────────┘
                     GET /api/v1/export   │  GET /api/v1/attestation
                                         ▼
                     export.json ──▶ verifier.py (third party, offline) → exit 0|1
```

## 2. Data model — `Event`

| Field | Type | Constraint | Role |
|---|---|---|---|
| `seq` | int | ≥ 1, no gaps, UNIQUE | sequence number |
| `ts` | str | ISO 8601 UTC, milliseconds | timestamp |
| `type` | str | 1–64 chars | `llm_call`, `llm_output`, `incident`, `eval`, any custom type |
| `payload` | object | arbitrary JSON | business content (GDPR minimization is caller responsibility in v0) |
| `prev_hash` | str | 64 hex | SHA-256 of event `seq-1` (`"0"×64` for genesis) |
| `event_hash` | str | 64 hex, UNIQUE | SHA-256 of canonical serialization of `{seq, ts, type, payload, prev_hash}` |
| `signature` | str | 128 hex | Ed25519 of `bytes.fromhex(event_hash)`, instance key |

**Canonical serialization**: `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")` — any third-party verifier implementation must produce the same bytes.

**Key**: Ed25519, PEM PKCS8 with chmod 600, created at database initialization (`<db>.key`). The public key alone is enough for verification.

## 3. Verification algorithm (third-party contract)

`verifier/verifier.py` — strict order, first failure wins:

1. `seq` of event n equals n (no gaps, no duplicates)
2. `prev_hash` equals `event_hash` of event n-1
3. `event_hash` equals the recomputed canonical SHA-256
4. `signature` is valid for the export public key
5. Attestation: `head_seq` = event count, `head_hash` = last `event_hash`, signature valid on the canonical summary
6. Each `anchor` event: referenced head is consistent with the chain, RFC 3161 token verified (`openssl ts -verify`) against that hash and the embedded TSA certificate — reports `anchors_checked` / `anchors_unverifiable`

Exit: **0** (valid) or **1** (first break + reason). The verifier never contacts the server (openssl only).

## 3bis. RFC 3161 anchoring (`anchor` event)

`POST /api/v1/anchors` seals the current chain head with a TSA (`NOIREBOX_TSA_URL` — self-hosted OpenSSL via `make tsa`, or any public TSA; ADR 006). The anchor is an ordinary event of type `anchor` whose payload contains:

| Field | Contents |
|---|---|
| `head_seq` | chain height at anchor time |
| `head_hash` | anchored chain head |
| `tsr` | RFC 3161 `TimeStampResp` token (base64 DER), signed by the TSA |
| `tsa_cert_pem` | root + leaf TSA bundle (PEM) — needed by the verifier |

The TSA only sees a SHA-256 digest (no data leaves the infrastructure). The verifier performs two checks for each anchor: consistency of `head_seq`/`head_hash` with the chain, then `openssl ts -verify` on the token against that hash and the embedded certificate. This is the control that catches a full chain regeneration by an operator with the private key.

## 4. Guardrail incident contract

The output is the same for both engines:

```json
{
  "category": "instruction_override|data_exfiltration|pii_request|tool_abuse",
  "score": 0.94,
  "excerpt": "…excerpt ≤ 120 chars…",
  "start": 214,
  "end": 305
}
```

- `regex` engine: FR/EN patterns compiled at load time, score = fixed severity.
- `ml` engine: TF-IDF classifier (1–2 word grams + 3–5 char grams) + multinomial logistic regression, trained on 5,400 FR examples (20% de-accented), confidence threshold 0.5, granularity = line.

## 5. API contract

Base: `http://127.0.0.1:8768` — full detail: [`openapi.json`](openapi.json).

| Route | Auth* | Body | Response |
|---|---|---|---|
| `POST /api/v1/token` | — | `{client_id, client_secret}` | `{access_token (JWT HS256, 1 h), token_type, expires_in}` |
| `POST /api/v1/events` | 🔒 | `{type, payload}` → 201 | sealed event |
| `GET /api/v1/events` | 🔒 | `?limit&offset` | paginated list |
| `GET /api/v1/verify` | — | — | `{valid, nb_events, first_error}` |
| `POST /api/v1/transcripts/scan` | 🔒 | `{meeting_id, text, engine, lang}` → 201 | incidents + journal entry |
| `GET /api/v1/attestation` | — | — | signed summary |
| `GET /api/v1/attestation.pdf` | — | — | A4 PDF (`application/pdf`, ~3.6 KB) |
| `POST /api/v1/attestation/verify` | — | attestation | `{valid}` |
| `POST /api/v1/anchors` | 🔒 | — → 201 | `{anchor_event_seq, anchored_head_seq, anchored_head_hash, tsr_bytes}` |
| `GET /api/v1/export` | 🔒 | — | `{format_version, service, public_key, events, attestation}` |

\* **Auth** (ADR 004): only enabled if `NOIREBOX_CLIENTS=id:secret,…` is set — 1-hour JWT HS256 in `Authorization: Bearer`, 60 req/min client rate limit (sliding window, 429 + `Retry-After`), constant-time secret comparison. **Verification routes remain open by design.**

Errors: 401 missing/invalid token (`WWW-Authenticate: Bearer`) · 422 Pydantic validation · 429 quota exceeded · 503 engine unavailable (actionable message) · verification failures always include exact location (`seq`).

## 6. Measured performance (MacBook M-series, local venv, 2026-09-27 — journal rows reproduced with `make bench`)

| Operation | Measure |
|---|---|
| Regex scan (7 lines) | **0.10 ms** |
| ML scan (7 lines, sklearn loaded) | **9.2 ms** (~1.3 ms/line) |
| Sealed append (SHA-256 + Ed25519 + SQLite commit) | **0.18 ms** |
| Full verification (100 events, incl. JSON load) | **45 ms** |

Therefore, sealed appends do not penalize the LLM call path significantly (seconds).
Absolute values vary with hardware and load — `make bench` on your machine is the reference.

## 7. v0.1.0 limits (assumed and tracked)

- No authentication or rate limiting (roadmap: OAuth2, see CHANGELOG)
- Unencrypted payloads: GDPR minimization is caller responsibility
- Private key on disk: HSM/KMS in roadmap; published attestation is the countermeasure
- Probabilistic guardrail: measured false negatives are non-zero
- Single-process append lock: sharding/scaling not targeted in v0

See [`THREAT-MODEL.md`](THREAT-MODEL.md) for the adversary model and [`ADRs.md`](ADRs.md) for the design decisions.
